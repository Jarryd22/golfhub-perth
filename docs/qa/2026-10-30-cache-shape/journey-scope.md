## Compatibility finding

No blocking compatibility issue was found in the focused shape checks. [`compatibility-review.json`](compatibility-review.json) records read-only AST/source inspection of the locally available exact heads for all 16 drafts #3–18. Across those refs, `serialise_result`, `make_snapshot` and the old `validate_snapshot` have identical ASTs. Every inspected core/direct `decorated_rows` constructor uses either `[]` or the `decorated` list returned by `decorate_rows`, which copies each row to a dictionary before appending it. This is source-format evidence, not a fresh remote-ref or published-payload validation.

The existing producer paths fit the new checks:

- `fetch_site_result` emits dictionary results for successful exact rows, empty results, unsupported rounds and provider failures. Exact rows are a list of dictionaries; the other paths use an empty list.
- `fetch_wembley_calendar_result` emits a dictionary with an empty decorated-row list plus calendar metadata. The rendered-Wembley source on PR #7 also uses the existing decorated-list path.
- `direct_result` emits a dictionary with empty rows. `refresh_cache_shard` builds dictionary error results for worker exceptions.
- `make_snapshot` serializes each result dictionary, removes the runtime `Site` object and emits a JSON `results` list. Stale reuse copies a valid prior result and adds metadata without changing its row container.

The repair preserves the schema version, empty `results`, missing or `null` `decorated_rows`, and lists containing dictionary rows. It does not require optional display, calendar, direct-link, error, weather or stale metadata. Existing rendered result variants remain representable without changing producers or migrating saved files. A non-dictionary course result or non-list/non-dictionary row structure makes the **whole snapshot unavailable**; it is not silently converted into a successful empty result. Discarding valid records alongside a malformed record is the deliberate small-boundary behavior; partial salvage would need a separate contract and broader work.

There is one shared-consumer effect to keep explicit: `scripts.refresh_cache_shard.load_previous_snapshot` also calls `validate_snapshot` and catches its `ValueError`. A malformed prior fallback snapshot now returns `None` there, so it cannot be reused. The fresh-provider majority gate, valid stale fallback rules and timestamps are unchanged. This is neither a production workflow run nor evidence that a currently published snapshot is malformed.

## Focused boundary, not a freshness rewrite

AST comparison finds only `validate_snapshot` changed in `app/shared_cache.py`; its other **nine** top-level functions are unchanged. In particular, snapshot construction, serialization, local save/load implementation, HTTP fetch order, cache naming and age-label calculation remain unchanged. Rejected fetched data reaches no save call, so a previously valid saved snapshot is retained. A rejected local file is treated as unavailable; the repair does not delete, rewrite or migrate that file.

The checks validate **containers**, not every field. Dictionary rows with invalid numeric values, absent required rendering keys, implausible capacities/times or nested malformed values may still require separate validation. URL trust, course membership, per-course freshness, weather completeness and semantic availability are outside this diff. Do not describe this as a complete JSON schema validator or a fix for every possible malformed-cache crash.

No canonical desktop/mobile files were copied into this branch, and no per-course freshness or selected-subset preservation repair was reimplemented. The prior backlog still applies: the desktop age badge uses payload publication time, per-course stale metadata is not fully presented, and selected-course live writes retain the existing snapshot replacement behavior. Source integration into the intended supported desktop/mobile baseline remains pending.
