## Behavior and edge cases

The original missing-single-date branch calls `search_live` while a previous terminal scan can still be owned; that method's ownership guard rejects the call. Neither cleanup path retained the rejected request. The controlled baseline demonstrates a stale checking message after both owners are released, with a manual retry still possible. This is a controller handoff defect, not proof of its natural frequency, a nonreturning worker or the historical Windows shutdown timeout.

The repair snapshots the submitted context only when a genuinely missing single-date result encounters retained scan ownership. A newer valid Find request clears that pending fallback before starting or queueing its own cache work; invalid controls preserve the prior valid request. Accepted closing cancels it. Scan cleanup releases the old references before consuming the pending context once, so it neither overlaps live ownership nor reads subsequently edited controls. Cache hits and multi-date handling retain their existing paths.

The explicit result-pending flag distinguishes a terminal worker awaiting cleanup from a newly accepted fallback whose thread may not yet report running. It becomes true only after a valid live request is accepted, and false in both terminal slots and ownership release. Cache cleanup therefore preserves Find and immediate progress clearing after a terminal cache hit, while keeping a new fallback busy before native startup. The final application contains this flag-based design; the alternative cleanup-only design discussed during review was not implemented.
