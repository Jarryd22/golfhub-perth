# Controlled cache-to-live handoff evidence

The confirmed gap occurs after a live request has reported its terminal result but still owns its thread reference. Find Tee Times is already usable. A new single-date cache miss tries to start its live fallback before the old owner is released; PR30 silently drops that fallback. Both owners can then be gone while the screen still says “Checking shared cache”. This controlled ordering does not establish how often it occurs in production.

The [before diagnostic](probe-before/probe.json) records four affected observations: live failure or cancellation, each with and without earlier displayed results. All four end with no cache/live owner, two constructed thread mocks and the checking-cache view. These are observational defect records, not four passing recovery assertions. The same run's two asserted controls pass: a cache hit during old-owner cleanup renders one row, and a cache miss after old-owner cleanup starts its fallback. The probe exits zero because its execution and controls completed without fixture errors.

The [after diagnostic](probe-after/probe.json) asserts recovery in all four affected cases: exactly one new fallback is started with the submitted **5 January 2033, 9 holes, one player, Morning, Araluen** context. It also retains both controls. The cache-hit control explicitly checks Find remains enabled and progress remains hidden immediately after cache cleanup while the previous live owner is still retained. There are six completed cases, zero callback errors and zero fixture failures. These diagnostic counts are separate from unittest counts.

The [before capture](probe-before/after-both-cleanups.png) and [after capture](probe-after/after-both-cleanups.png) were inspected at 980×640. The first shows the stranded checking-cache view after both owners were released. The second shows the active live-refresh header, progress bar, Stop action and checking-live text after the fallback starts. The visible text fits these captures. The new fallback's worker body is deliberately never executed.

The final [regression baseline](baseline/result.json) uses the exact PR30 checkout `a3e522b5e2d79856f994fb342a7c6b1253a1143d`: **22 methods, 14 passed, eight failed, zero errors/skips**. The identical final file on the [repair source](final-focused/result.json) passes **22/22**, with zero errors/skips. All original ten test methods and original helper function ASTs remain unchanged; twelve methods were added. Coverage includes all three terminal outcomes and both cleanup orders, actual Find clicks, submitted versus pending controls, intercepted result-save and BOOK context, newest queued single and multi-date searches, invalid new parameters, close cancellation, cache-hit preservation, and busy controls while the new fallback is owned but reports `isRunning=False`. That last case is a controlled ownership check, not native timing evidence.
